## 0. RC2 — Dialogue Timeline Projection (real-data finding)

The first real-data run of M4.2a RC1 against CHATGPT-ACQ-001 proved that
the RC1 candidate domain was conceptually wrong.

RC1 generated a candidate for every consecutive pair of *current-path
message nodes*, without distinguishing end-user-visible dialogue turns
(`text`, `multimodal_text`) from non-visible internal/technical message
nodes (`thoughts`, `reasoning_recap`). Measured on CHATGPT-ACQ-001:

- current-path message nodes: 32,679
- visible dialogue messages (text + multimodal_text): 26,187
- non-visible current-path message nodes (thoughts + reasoning_recap): 6,492
- RC1 candidates: 31,902
- of RC1's 6,617 assistant->assistant transitions, >99% (6,571) involved
  at least one non-visible node on one side — i.e. they were artifacts of
  candidate vertices that were never actually dialogue turns, not real
  episode boundaries.

This is a critical distinction:

    ACNF current-path message graph  !=  Dialogue Timeline Projection

M4.1 preserves **all** current-path message nodes losslessly — visible and
non-visible alike — because ACNF's job is lossless normalization, not
episode-observable selection.

M4.2a's job is different: it selects only the subset of current-path
message nodes that were actually observable dialogue turns (the
*Dialogue Timeline Projection*), while still preserving the fact that
non-visible nodes were skipped, as provenance on the surrounding
candidate. It does **not** generate candidate boundaries against
technical/non-visible message nodes.

Pipeline (RC2, supersedes the RC1 pipeline in section 1):

    ACNF current path
            |
            v
    Dialogue Timeline Projection
            |
            v
    visible dialogue nodes
            |
            v
    consecutive visible-node pairs
            |
            v
    BoundaryCandidate (+ intermediate provenance)

Projected on CHATGPT-ACQ-001, this yields:

    26,187 visible dialogue messages
    25,410 projected boundary candidates   (26,187 - 777 conversations)

See section 3 for the full updated baseline, section 6a for the
projection algorithm, section 7a for intermediate-node provenance, and
section 16 for the updated CHATGPT-ACQ-001 baseline gate. The RC1 baseline
of 31,902 candidates is no longer the expected M4.2a result; it remains
documented here only as the finding that motivated RC2.

RC1 and RC2 candidate identities are kept from colliding via
`feature_version`: RC1 candidates carry `m4.2a-0.1`, RC2 candidates carry
`m4.2a-0.2` (see `tools/episodes/models.py`, `FEATURE_VERSION`).

This is not a scoring calibration pass — section 13 (`candidate score`)
and its weights/thresholds are unchanged from RC1. A second real-data
measurement over the corrected candidate domain is needed before deciding
whether scoring needs calibration.

## 1. Obiettivo

M4.2a introduce il primo livello di segmentazione della memoria professionale.

Il componente NON deve decidere definitivamente gli episodi.

Deve analizzare ogni transizione tra due messaggi *visibili* consecutivi
appartenenti al current path di una conversazione (vedi sezione 0 — la
Dialogue Timeline Projection) e produrre feature deterministiche,
spiegabili e riproducibili che possano indicare la presenza di un possibile
episode boundary.

Pipeline (RC2):

    ACNF current path
            |
            v
    Dialogue Timeline Projection
            |
            v
    visible dialogue nodes
            |
            v
    consecutive visible-node pairs
            |
            v
    deterministic feature extraction
            |
            v
    candidate boundary records (+ intermediate provenance)

La decisione finale SAME_EPISODE / NEW_EPISODE / UNCERTAIN appartiene
alla milestone M4.2b.

M4.2a non modifica ACNF.

## 4. Episode boundary concept

A possible episode boundary exists when the conversational work changes
substantially along one or more dimensions:

- GOAL
- PROBLEM
- OPERATIONAL TASK
- DECISION CONTEXT
- PROJECT PHASE

A lexical or technological change alone is not sufficient.

Example likely SAME EPISODE:

    installiamo Zabbix
    PostgreSQL non parte
    correggiamo docker-compose
    Zabbix ora funziona

The technologies change, but the operational goal remains the same.

Example likely NEW EPISODE:

    bene, Zabbix funziona
    ora passiamo alla VPN

even if only seconds separate the messages.

## 5. Input selection

Use only nodes satisfying:

    has_message == true
    is_current_path == true
    is_technical_root == false

This yields the full current-path *message-node* set — visible dialogue
nodes and non-visible technical nodes (thoughts, reasoning_recap) alike.
It is the input to the Dialogue Timeline Projection (section 6a), not yet
the candidate-vertex set.

Off-current-path nodes remain preserved in ACNF but do not participate in
M4.2a v0.1.

Process each conversation independently.

No boundary may cross conversation boundaries.

---

## 6. Ordering

Do NOT sort messages merely by timestamp.

Reconstruct current-path order from the graph:

    current_node_id
        -> parent_id chain
        -> reverse

This is the canonical message order for M4.2a, and remains authoritative
end to end: the Dialogue Timeline Projection (section 6a) only filters
this ordered sequence down to its visible subsequence — it never
re-derives order from timestamps or role.

Timestamps are metadata/features only.

---

## 6a. Dialogue Timeline Projection (RC2)

Implemented in `tools/episodes/projection.py`.

Given the ordered current-path message-node list from section 6, project
it onto the subsequence of nodes whose `content_type` is a v0.1 visible
dialogue type (section 7a — `VISIBLE_DIALOGUE_CONTENT_TYPES`). Non-visible
nodes between two visible nodes are not discarded: they are carried
forward as ordered intermediate provenance, attached to the candidate
built from the visible node that follows them.

Non-visible nodes before the first visible node have no preceding visible
node to attach provenance to and are dropped (they cannot precede a
candidate that does not exist). Non-visible nodes after the last visible
node are likewise never attached to any candidate.

Example:

    USER text node A
       ->
    ASSISTANT thoughts node X
       ->
    ASSISTANT reasoning_recap node Y
       ->
    ASSISTANT text node B

produces one candidate `A -> B`, never `A -> X`, `X -> Y`, or `Y -> B`.

---

## 7. Candidate unit

For each consecutive pair of *visible dialogue nodes* (section 6a):

    visible_message_i
    visible_message_i+1

produce exactly one BoundaryCandidate record.

A conversation with V visible dialogue messages therefore produces:

    max(V - 1, 0)

candidate records — not `current_path_message_count - 1`. See section 16
for the updated invariant and section 3 / section 16 for the corpus-wide
numbers this implies on CHATGPT-ACQ-001.

---

## 7a. Content-type visibility policy

Defined explicitly in `tools/episodes/projection.py`:

    VISIBLE_DIALOGUE_CONTENT_TYPES = {
        "text",
        "multimodal_text",
    }

`thoughts` and `reasoning_recap` remain preserved in ACNF but are NOT
boundary vertices for v0.1 — they may still appear as intermediate
provenance (section 7b) on the candidate that skips over them.

Visibility is a content-type/domain decision, not `len(text) > 0`: a
`text` node with empty parts is still a visible dialogue node. This
matters because a legitimate visible message may carry an empty string.

Unknown content types are treated as non-visible for the projection,
preserved in ACNF, and never cause a crash.

---

## 7b. Intermediate node provenance

When two consecutive visible dialogue nodes are separated on the current
path by one or more non-visible message nodes, that fact is preserved on
the resulting BoundaryCandidate via three fields (section 8):

    intermediate_node_ids
    intermediate_content_types
    intermediate_node_count

Ordered as encountered on the current path. Content is never copied into
the candidate — ACNF remains the authoritative source if the skipped
nodes' content is needed later (section 2.5).

For the example in section 6a, the `A -> B` candidate carries:

    intermediate_node_ids = [X, Y]
    intermediate_content_types = ["thoughts", "reasoning_recap"]
    intermediate_node_count = 2

A candidate between two directly adjacent visible nodes (no non-visible
node skipped) carries `intermediate_node_count == 0` and empty lists.

## 9. Text extraction

Feature extraction should operate only on user-visible textual portions
of the ACNF node content when available.

Do not destroy or rewrite ACNF content.

Implement a deterministic text-extraction helper able to handle at least:

- text
- multimodal_text

For content types without usable visible text:

- return empty text;
- keep the candidate record;
- do not fabricate content.

Do not use thoughts/reasoning_recap as semantic boundary text by default
unless they are explicitly user-visible according to the ACNF representation.

Unknown content types must not crash the pipeline.

RC2 note: since `before_node`/`after_node` are now always visible
dialogue nodes (section 6a), this extraction is only ever invoked on
`text`/`multimodal_text` nodes in practice — thoughts/reasoning_recap
nodes never reach it as a candidate endpoint, only as intermediate
provenance (section 7b), where their content is never extracted or
copied. `extract_visible_text` behavior itself is unchanged from RC1.

## 10. Time-gap feature

Compute:

    time_gap_seconds = after_created_at - before_created_at

for the two visible boundary endpoints, when both timestamps are valid
and non-decreasing. Timestamps of skipped intermediate nodes (section 7b)
are never used — they are provenance, not boundary endpoints.

Otherwise:

    time_gap_seconds = null

and optionally record a diagnostic reason.

Suggested deterministic buckets:

- LT_1M
- 1M_5M
- 5M_15M
- 15M_30M
- 30M_1H
- 1H_3H
- 3H_12H
- 12H_1D
- 1D_7D
- GE_7D
- UNKNOWN

Bucket boundaries must be explicit and unit-tested.

Do NOT classify a boundary from time alone.

## 12. Lexical similarity

Implement a lightweight deterministic lexical comparison between the
visible text before and after the boundary.

No embedding model.

Preferred v0.1 approach:

- Unicode-aware lowercasing;
- simple tokenization;
- remove punctuation;
- optionally remove a small deterministic stopword set;
- compute Jaccard similarity or cosine similarity over token-frequency
  vectors.

Avoid third-party NLP dependencies.

Output:

    lexical_similarity ∈ [0,1]
    lexical_shift_score = 1 - lexical_similarity

This feature is informative only.

A high lexical shift does not automatically imply a new episode.

## 13. Candidate score

M4.2a v0.1 may use a transparent weighted heuristic.

Example conceptual components:

- time gap contribution
- opening marker contribution
- closure marker contribution
- transition marker contribution
- resume marker negative contribution
- lexical shift contribution

Do not hide weights.

Weights must live in a named configuration object/constants and be
documented.

Candidate score should be normalized to a stable range, preferably:

    0.0 .. 1.0

Suggested classes:

LOW    < 0.35
MEDIUM 0.35 .. < 0.65
HIGH   >= 0.65

Exact initial values may be adjusted during benchmark calibration, but
must not be learned silently from the real corpus.

**Semantics (Gold Pilot 001 finding — see section 26):** `candidate_score`
must be read as a **Boundary Evidence Score**, not as a probability of a
semantic episode boundary. `HIGH` means "strong deterministic evidence
according to the available structural, lexical, temporal and marker
features" — it does not mean "high probability that a semantic episode
boundary exists". This is a documentation clarification only; the weights,
thresholds, and computation in this section and in `scoring.py` are
unchanged.

## 14. Reasons

Every candidate must contain human-readable machine-generated reasons,
for example:

- "time_gap=14.2h"
- "opening_marker=ora passiamo"
- "closure_marker=ora funziona"
- "resume_marker=riprendiamo"
- "lexical_shift=0.78"

Reasons are diagnostic metadata, not source content.

---

## 15. Deterministic hashing

candidate_hash must be SHA-256 over canonical candidate content excluding
operational metadata. This includes the `intermediate_*` provenance
fields (section 7b/8): skipping a different set of non-visible nodes
between the same before/after pair is a materially different candidate,
so it must change the hash.

candidate_id should be deterministic.

Preferred basis:

    conversation_id
    before_node_id
    after_node_id
    feature_version

No random UUIDs.

RC2 bumped `feature_version` from `m4.2a-0.1` to `m4.2a-0.2` (see
`tools/episodes/models.py`) specifically because the candidate-vertex
semantics changed materially (section 0/6a) — this keeps RC1 and RC2
candidate identities from colliding even for a `(conversation_id,
before_node_id, after_node_id)` triple that happens to exist in both.

Two identical runs must produce byte-identical candidate JSONL.

## 16. Output

Preferred:

    boundary_candidates.jsonl
    boundary_validation.json

One JSONL record per consecutive *visible dialogue node* pair (section
6a/7) — not per consecutive current-path message pair.

No database in M4.2a.

## 21. Definition of Done

M4.2a is complete when:

1. current-path order is reconstructed from ACNF graph;
2. the current path is projected onto its visible dialogue subsequence
   (Dialogue Timeline Projection, section 6a) before candidate generation;
3. every consecutive *visible dialogue node* pair produces one candidate,
   never a pair involving a non-visible node as an endpoint;
4. skipped non-visible nodes are preserved as intermediate provenance on
   the surrounding candidate (section 7b), never as candidate content;
5. all features are deterministic;
6. time-gap buckets are tested, and use visible-endpoint timestamps only;
7. marker extraction is tested;
8. lexical feature is tested;
9. score/reasons are transparent;
10. candidate IDs/hashes are deterministic, and hashes are sensitive to
    intermediate-node provenance;
11. synthetic graph and projection tests pass;
12. real CHATGPT-ACQ-001 visible-dialogue-message and candidate counts
    are structurally correct (26,187 visible dialogue messages, 25,410
    candidates — section 0/3/17);
13. two real runs produce byte-identical boundary_candidates.jsonl;
14. no ACNF data is modified.

## 23. Gold Pilot 001 — methodology and results

A deterministic pilot of 60 boundary candidates was drawn from the RC2
candidate output on CHATGPT-ACQ-001 (20 `HIGH`, 20 `MEDIUM`, 20 `LOW`, by
`candidate_class`) and manually reviewed by a human annotator against the
gold label set defined in section 18 (`SAME_EPISODE` / `NEW_EPISODE` /
`UNCERTAIN`, recorded here as `FALSE` / `TRUE` / `AMBIGUOUS` respectively
— `TRUE` means the candidate was manually judged to be a real semantic
episode boundary).

This is a **pilot**, not the full ~1,200–1,500-transition gold dataset
described in section 18 — it exists to sanity-check the deterministic
features against a small, hand-labeled real sample before further gold
annotation work is scheduled. Per section 14 of the closure-pass
instructions, only aggregate findings and anonymized candidate IDs are
recorded here; no personal conversation content is copied into this
document.

Aggregate gold labels (N=60):

    TRUE       = 5
    FALSE      = 54
    AMBIGUOUS  = 1

Breakdown by `candidate_class`:

    HIGH   (N=20): TRUE=3,  FALSE=16, AMBIGUOUS=1
    MEDIUM (N=20): TRUE=2,  FALSE=18, AMBIGUOUS=0
    LOW    (N=20): TRUE=0,  FALSE=20, AMBIGUOUS=0

True boundary IDs in the pilot (anonymized pilot identifiers, not ACNF
node/conversation IDs): `GOLD-008`, `GOLD-009`, `GOLD-012`, `GOLD-032`,
`GOLD-040`.

Ambiguous: `GOLD-010`.

Reading this table: `HIGH` candidates concentrate a larger share of true
boundaries than `MEDIUM` or `LOW` (3/20 vs 2/20 vs 0/20), which is
consistent with the score behaving as ordinal evidence. But even within
`HIGH`, the large majority (16/20) were manually judged `FALSE` — this is
the empirical basis for section 26's conclusion that `candidate_score`
must be read as evidence strength, not as a boundary probability.

FALSE time-gap buckets: `LT_1M`=32, `1M_5M`=14, `5M_15M`=6, `15M_30M`=1,
`30M_1H`=1.

**Interpretation:** long time gaps are strongly informative in this pilot
— `TRUE` candidates have a median gap almost four orders of magnitude
larger than `FALSE` candidates — but they are not sufficient on their own:
2 of the 5 `TRUE` boundaries occurred within `LT_1M`, indistinguishable by
time gap alone from the bulk of `FALSE` candidates. This confirms the
section 3 conclusion (time gap is a feature, never a standalone boundary
rule) directly against gold-labeled data, and is why `time_gap_weight` in
`scoring.py` is deliberately capped low (section 13).

## 25. Gold Pilot 001 — lexical shift (Jaccard) finding

    TRUE      (N=5):  min=0.923  mean=0.964  median=0.968  max=0.997
    FALSE     (N=54): min=0.613  mean=0.936  median=0.957  max=1.000
    AMBIGUOUS (N=1):  0.995

**Conclusion:** lexical shift based on message-to-message Jaccard overlap
(section 12) is **weakly discriminative** for semantic episode boundaries
in this pilot. Normal user/assistant dialogue frequently has low lexical
overlap (i.e. high `lexical_shift_score`) even when both turns belong to
the same episode — the `FALSE` distribution's median (0.957) is nearly
identical to the `TRUE` distribution's median (0.968), and the `FALSE`
range fully covers the `TRUE` range from below.

This is expected: role changes (user asking, assistant answering) alone
already produce large token-set differences, independent of whether an
episode boundary occurred. `lexical_shift` must therefore be treated as
**supporting evidence only**, never as a standalone signal. Per the
closure-pass instructions, `lexical.py` and its weight in `scoring.py` are
unchanged in this pass — this finding is recorded for a future, explicit
benchmark/calibration pass (M4.2b or later), not acted on here.

## 26. Gold Pilot 001 — marker findings

Marker presence rate by gold label (N as in section 23):

    OPEN:   TRUE 3/5 (60.00%)   FALSE 18/54 (33.33%)   AMBIGUOUS 1/1
    CLOSE:  TRUE 1/5 (20.00%)   FALSE  4/54  (7.41%)
    RESUME: 0 occurrences in the pilot (neither TRUE nor FALSE)
    TRANS:  TRUE 2/5 (40.00%)   FALSE 28/54 (51.85%)   AMBIGUOUS 1/1

**Conclusions:**

- Opening (`OPEN`) and closure (`CLOSE`) markers appear at roughly
  1.8x–2.7x the rate in `TRUE` candidates versus `FALSE` candidates in
  this pilot — they add real evidence, consistent with their positive
  weight in `scoring.py`.
- Transition (`TRANS`) markers are **not independently discriminative**
  in this pilot: they actually appear at a *higher* rate in `FALSE`
  candidates (51.85%) than in `TRUE` candidates (40.00%). This does not by
  itself justify a weight change (no tuning is authorized in this pass —
  section 8 of the closure-pass instructions) but is recorded so a future
  calibration pass can evaluate it against the full gold dataset, not this
  60-candidate pilot.
- `RESUME` markers did not occur in the pilot sample at all — no
  conclusion can be drawn from this pilot about their discriminative
  power; `resume_marker_weight`'s negative sign (section 13) remains a
  design assumption, not yet gold-validated.
- No marker category, alone or combined, should be interpreted as proof
  of an episode boundary. All are supporting evidence within the
  Boundary Evidence Score (section 26 below).

## 27. Fundamental architectural conclusion — Boundary Evidence Score

The Gold Pilot 001 results (sections 23–26) confirm what the RC2 dialogue
timeline projection work (section 0) already implied structurally: **M4.2a
is not a semantic episode segmenter.**

Its correct role is:

**DETERMINISTIC BOUNDARY EVIDENCE ENGINE**

M4.2a produces explainable, reproducible evidence about every projected
dialogue transition (section 6a/7) — deterministic features, a
transparent weighted score, and human-readable reasons (section 13/14).
It does not, and by design cannot, decide whether a transition is a real
semantic episode boundary: none of its four evidence families (time gap,
markers, lexical shift, and their combination in `candidate_score`) is
individually or jointly sufficient, as sections 24–26 show directly
against gold-labeled data.

`candidate_score` and `candidate_class` must therefore be documented and
read conceptually as a:

**BOUNDARY EVIDENCE SCORE**

and explicitly **not** as:

**probability of semantic boundary**

`HIGH` means: "strong deterministic evidence according to the available
structural, lexical, temporal and marker features."

`HIGH` does **not** mean: "high probability that a semantic episode
boundary exists" — Gold Pilot 001 section 23 shows 16 of 20 `HIGH`
candidates were manually judged `FALSE`.

This is a documentation/interpretation clarification only. No scoring
code, weight, or threshold changes as a result of this finding (section 8
of the closure-pass instructions) — see section 13's amended note and
`tools/episodes/scoring.py`'s module docstring, both updated to carry this
same clarification without altering behavior.

        ->

The "future semantic resolution layer" and "SEMANTIC EPISODES" stages are

`BOUNDARY CANDIDATES` output correctly in the overall Atlas V2 memory
pipeline: M4.2a's output is the *input* to that future layer, not a
replacement for it.

## 29. Parking Lot / Future Investigation

The following ideas were identified during the M4.2a real-data and Gold
Pilot 001 work but are explicitly **out of scope** for M4.2a and were not
designed, prototyped, or implemented in this or any prior M4.2a pass:

- contextual windows (comparing a candidate against surrounding dialogue
  context, not just its two immediate endpoints);
- dialogue-window comparison;
- embeddings;
- semantic similarity (beyond lexical/Jaccard);
- LLM episode resolver;
- scoring redesign (new weights, new features, new thresholds);
- additional heuristic marker mining (expanding the lexicon beyond
  section 11 based on gold data);
- intra-message episode boundaries (a single message spanning more than
  one episode).

These are recorded so future milestone planning (M4.2b or later) has a
starting point. No ADRs, designs, or implementations for any of these
items were created in this pass.

## 30. M4.2a — final status

M4.2a is a **Deterministic Boundary Evidence Engine**, not a **Semantic
Episode Segmenter**.

It reliably and reproducibly identifies *where* a transition between two
visible dialogue turns carries deterministic evidence of a possible
episode boundary, and *why* (section 14, `reasons`) — but the *whether*
remains, by design, for a future semantic resolution layer (section 28)
that is explicitly out of scope here (section 20, section 29).

RC2's Dialogue Timeline Projection (section 0/6a) and Gold Pilot 001
(sections 23–27) are both real-data-verified. No further redesign,
scoring changes, or new features are authorized in this closure pass.
