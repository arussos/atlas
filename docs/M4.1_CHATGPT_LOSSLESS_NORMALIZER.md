# M4.1 — ChatGPT Lossless Normalizer

## Stato

Milestone: M4.1  
Componente: Atlas V2  
Tipo: deterministic ingestion layer  
Input primario: OpenAI ChatGPT Data Export ZIP  
Output: Atlas Conversation Normal Form — ACNF v0.1

---

## 1. Obiettivo

M4.1 introduce il primo livello deterministico della nuova architettura Atlas.

Il componente deve trasformare un export ChatGPT ufficiale nel formato
normalizzato Atlas senza effettuare:

- interpretazione semantica;
- summarization;
- classificazione mediante LLM;
- embedding;
- vector indexing;
- knowledge extraction.

Il normalizzatore deve preservare la struttura necessaria per ricostruire
fedelmente il patrimonio conversazionale originale.

Il RAW OpenAI rimane sempre la sorgente autorevole.

---

## 2. Principi architetturali

### 2.1 RAW immutable

L'export ZIP originale non deve mai essere modificato.

Il normalizzatore opera esclusivamente in lettura sul RAW.

### 2.2 Deterministic

Lo stesso input deve produrre lo stesso output normalizzato.

Run ripetuti sullo stesso export devono produrre gli stessi hash canonici.

### 2.3 Lossless for professional memory

Devono essere preservati almeno:

- conversation identifiers;
- conversation metadata;
- node identifiers;
- message identifiers;
- parent relationships;
- current node;
- current path;
- branch/off-path nodes;
- author role;
- content type;
- visible message content;
- timestamps;
- asset references;
- OpenAI source identifiers.

### 2.4 Model independent

ACNF non deve dipendere da:

- Ollama;
- Open WebUI;
- Qdrant;
- uno specifico LLM;
- uno specifico embedding model.

### 2.5 Source provenance

Ogni elemento normalizzato deve poter essere ricondotto al relativo elemento
dell'export sorgente.

## 4. OpenAI graph model

Ogni conversazione contiene un `mapping`.

Ogni mapping node contiene:

- `id`
- `parent`
- `message`

Ogni conversazione contiene esattamente un root node tecnico:

- parent = null
- message = null

CHATGPT-ACQ-001 contiene:

- 777 conversazioni
- 777 technical roots
- 0 anomalie

Il technical root deve essere preservato come struttura, ma non deve essere
trattato come messaggio utente/assistant.

---

## 5. Current path e branching

La conversazione non deve essere normalizzata come semplice sequenza temporale.

Devono essere preservati:

- parent relationship;
- current_node;
- current path;
- off-current-path nodes.

Ogni node normalizzato deve contenere:

- `is_current_path`
- `is_technical_root`

Gli off-path nodes non vengono eliminati.

Il retrieval futuro potrà privilegiare il current path senza perdere la
storia alternativa.

---

## 6. Asset model

L'export utilizza file fisici `.dat`.

`conversation_asset_file_names.json` associa:

    physical export filename
        ->
    original filename

Esempio:

    file-2DDLLAw1iPRMn5T7MiTVqFLC.dat
        ->
    image.png

I messaggi multimodali possono riferire gli asset mediante:

    file-service://file-2DDLLAw1iPRMn5T7MiTVqFLC

Il normalizzatore deve preservare la relazione:

    conversation
        ->
    message
        ->
    asset reference
        ->
    physical export asset
        ->
    original filename

`library_files.json` costituisce una sorgente metadata separata e deve essere
preservata come tale.

---

### 6.1 Asset storage classes — RC1 real-data finding (M4.1 RC2)

Il primo run reale su CHATGPT-ACQ-001 (RC1) ha rilevato 244 anomalie:
122 `unresolved_asset_filename` + 122 `missing_physical_asset`, tutte
riconducibili a esattamente 122 asset id distinti. L'ispezione forense ha
dimostrato che tutti e 122 usano lo schema di pointer:

    sediment://

e che l'id referenziato (es. `sediment://file_0000000098dc71f6889f91e3db3e2290`)
non esiste come membro fisico nello ZIP — appare solo dentro il JSON delle
conversazioni.

Conclusione: l'export ChatGPT espone due classi di storage per gli asset
referenziati nei messaggi:

- `file-service://` — asset **esportato**: l'export è tenuto a contenere il
  payload fisico `<asset_id>.dat`; se manca, resta un'anomalia reale.
- `sediment://` — asset **reference-only**: riferimento logico osservato
  solo dentro il JSON conversazionale, senza payload fisico nello ZIP.
  L'assenza del `.dat` per questa classe è un comportamento noto della
  sorgente OpenAI, non una perdita di dati.

Il normalizzatore modella questa distinzione con un campo esplicito e
deterministico su `AssetRecord`, `storage_kind` (`exported` /
`reference_only`), determinato dallo schema del pointer combinato con la
reale presenza fisica del `.dat` nello ZIP — non da un'assunzione fissa
che ogni asset referenziato debba risolvere a un file fisico. Per un
asset `reference_only`: `physical_filename`, `sha256` e `size_bytes`
restano `None`, e non vengono più emesse le anomalie
`missing_physical_asset` / `unresolved_asset_filename` per la sola
assenza di un file fisico o di una voce in
`conversation_asset_file_names.json`. La validazione per gli asset
`file-service://`/`exported` non è stata indebolita: un `.dat` atteso e
assente per questa classe resta un'anomalia reale.

Metriche generiche aggiunte (dataset-independent): `logical_assets`
(totale asset logici distinti, qualunque `storage_kind`) e
`reference_only_assets`. Per CHATGPT-ACQ-001: `logical_assets = 6364`,
`physical_dat_assets = 6242`, `reference_only_assets = 122`
(6242 + 122 = 6364).

### 6.2 Library file identity — RC3 real-data finding

L'ispezione reale di tutti i 2,136 record di `library_files.json` in
CHATGPT-ACQ-001 ha confermato una struttura di identità regolare e
costante su tutto il corpus:

    raw["id"] = {
        "id": "libfile_...",
        "partition_key": "libfile_..."
    }
    raw["file_id"] = "file_..."

con `raw.id` e `raw.file_id` sempre presenti, e `raw.id["id"]` /
`raw.file_id` entrambi univoci su tutti i 2,136 record (0 duplicati, 0
mancanti).

Questa è una struttura a due identità distinte, non un identificatore
singolo: `LibraryFileRecord` le espone entrambe separatamente anziché
collassarle in un unico campo o memorizzare l'intero oggetto raw come
identità scalare:

- `library_file_id` -> `raw["id"]["id"]`, l'identità del *record* libreria
  (`libfile_*`).
- `source_file_id` -> `raw["file_id"]`, l'identità del *file sorgente*
  referenziato (`file_*`).

`raw["id"]["partition_key"]`, e ogni altro campo metadata sorgente, non
vengono scartati: sopravvivono verbatim in `raw_record`, insieme a
`raw["id"]["id"]` e `raw["file_id"]` stessi. `raw_record` resta la fonte
completa e non lossy; `library_file_id`/`source_file_id` sono comodità
scalari derivate, non sostituti.

Il normalizzatore resta difensivo anche se la baseline reale è
perfettamente regolare:

- se `raw["id"]` è assente o non ha la forma `{"id": <str>, ...}`, viene
  assegnato un `library_file_id` di fallback deterministico
  (`synthetic-libfile-<sha256 canonico del record raw>`, mai un UUID
  casuale) e viene registrata un'anomalia `malformed_library_file_id`;
  `raw_record` resta comunque preservato integralmente;
- run ripetuti sullo stesso record malformato producono lo stesso
  `library_file_id` di fallback;
- se `raw["file_id"]` è assente, `source_file_id` resta `None` e viene
  registrata un'anomalia `missing_library_file_source_id`, senza alcun
  effetto sulla risoluzione o determinismo di `library_file_id`.

## 7. ACNF v0.1 output

La prima implementazione utilizza JSONL.

Output previsto:

    normalized/
    ├── acquisition.json
    ├── conversations.jsonl
    ├── nodes.jsonl
    ├── assets.jsonl
    ├── library_files.jsonl
    └── validation.json

### acquisition.json

Contiene almeno:

- acquisition_id
- source_filename
- source_sha256
- normalized_schema_version
- exporter/version metadata
- normalization timestamp

Il timestamp operativo non deve partecipare agli hash canonici.

### conversations.jsonl

Una record per conversazione.

Campi minimi:

- conversation_id
- source_id
- title
- created_at
- updated_at
- current_node_id
- default_model_slug
- archived
- starred
- memory_scope
- node_count
- message_count
- has_branches
- conversation_hash

### nodes.jsonl

Una record per mapping node.

Campi minimi:

- conversation_id
- node_id
- parent_id
- message_id
- role
- created_at
- content_type
- content
- asset_refs
- is_technical_root
- is_current_path
- node_hash

### assets.jsonl

Campi minimi:

- asset_id
- physical_filename
- original_filename
- mime_type
- size_bytes
- sha256
- storage_kind (`exported` / `reference_only` — vedi 6.1)
- asset_hash

`AssetRecord` è deduplicato globalmente per `asset_id` sull'intero export,
quindi non porta provenance (quale conversazione/nodo/messaggio ha
referenziato l'asset): la provenance a livello di occorrenza vive in
`NodeRecord.asset_refs` (`{"asset_id", "pointer_uri", "content_type"}` per
ogni nodo che referenzia l'asset), non su `AssetRecord`. Non esistono più
campi `source_conversation_id`/`source_message_id` su `AssetRecord`.

### library_files.jsonl

Una record per voce di `library_files.json`, sorgente metadata separata
dagli asset referenziati nei messaggi (vedi 6.2).

Campi minimi:

- library_file_id (`raw["id"]["id"]`, con fallback deterministico se
  assente/malformato — vedi 6.2)
- source_file_id (`raw["file_id"]`, `None` se assente)
- raw_record (l'intero oggetto sorgente, preservato losslessly)

I campi non disponibili devono poter essere null.

## 8. Canonical hashing

Gli hash Atlas devono essere deterministici.

La serializzazione canonica utilizza:

- UTF-8
- JSON
- chiavi ordinate
- separatori stabili
- nessuna formattazione dipendente dall'ambiente

Hash algorithm:

    SHA-256

Sono previsti almeno:

- node_hash
- conversation_hash
- asset_hash

I metadati operativi non semantici non devono alterare gli hash.

## 9. Delta readiness

M4.1 non implementa ancora il delta engine.

Deve però produrre gli identificatori e gli hash necessari affinché una
successiva milestone possa classificare:

- NEW
- UPDATED
- UNCHANGED
- REMOVED / NOT PRESENT

tra acquisizioni differenti.

## 10. Validation gates

CHATGPT-ACQ-001 deve produrre esattamente:

- conversations = 777
- nodes = 33,642
- messages = 32,865
- technical roots = 777
- conversations with branches = 65
- off-current-path nodes = 186
- conversation asset mappings = 6,146

Qualsiasi divergenza deve causare validation failure.

Dopo la RC1 (vedi 6.1), i gate opzionali `chatgpt-acq-001` includono anche
`logical_assets = 6364` e `reference_only_assets = 122`, in aggiunta —
non in sostituzione — ai 10 gate sopra.

## 11. Security and privacy

I dati reali dell'export ChatGPT:

- non devono essere committati;
- non devono entrare nei test Git;
- non devono essere copiati nel repository.

I test devono utilizzare fixtures sintetiche.

Il path del RAW deve essere fornito a runtime.

## 12. Explicit non-goals M4.1

M4.1 NON implementa:

- RAG;
- Qdrant ingestion;
- embeddings;
- semantic chunking;
- episode segmentation;
- project classification;
- decision extraction;
- problem/solution extraction;
- summarization;
- LLM inference;
- BookStack/Snipe-IT agents.

Questi layer saranno costruiti sopra ACNF.

## 13. Definition of Done

M4.1 è completata quando:

1. il RAW ZIP viene letto direttamente senza modifica;
2. tutti gli shard conversazionali vengono scoperti automaticamente;
3. tutte le conversazioni vengono normalizzate;
4. il conversation graph è preservato;
5. il current path è ricostruito correttamente;
6. branch e off-path nodes sono preservati;
7. asset references sono preservati;
8. gli output sono deterministici;
9. la baseline CHATGPT-ACQ-001 supera tutti i validation gates;
10. due run consecutivi producono gli stessi hash canonici;
11. tutti i test automatici passano.
