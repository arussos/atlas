# M4.2b-A — Semantic Boundary Resolver: Contract + Evaluator

Status: **PASS 1 (M4.2b-A) — infrastructure only, no real LLM provider. PASS 2 (M4.2b-B) — first real local judge (Ollama), implementation-only: no real Gold Pilot run performed yet (§16). PASS 3 (M4.2b-C) — Semantic Judge Instruction v0.2, prompt-only experiment: no real Gold Pilot run performed yet (§17).**

## 1. Why M4.2b exists

M4.1 (Lossless Normalizer) and M4.2a (Deterministic Boundary Evidence
Engine) are CLOSED. The verified pipeline is:

```
RAW CHATGPT EXPORT
    -> M4.1 LOSSLESS NORMALIZER
    -> ACNF / SOURCE GRAPH
    -> CURRENT PATH
    -> DIALOGUE TIMELINE PROJECTION
    -> VISIBLE DIALOGUE TRANSITIONS
    -> M4.2A DETERMINISTIC BOUNDARY EVIDENCE
    -> BOUNDARY CANDIDATES
```

Gold Pilot 001 (60 hand-labeled real candidates: 20 HIGH / 20 MEDIUM / 20
LOW by `candidate_class`; manual labels 5 TRUE / 54 FALSE / 1 AMBIGUOUS)
established that `candidate_score`/`candidate_class` are a **Boundary
Evidence Score**, not a probability of a semantic boundary. M4.2a
generates evidence; it does not decide.

## 2. Verified limitation of M4.2a

M4.2a cannot and does not distinguish, purely from deterministic
features, cases such as:

- question -> answer (not a boundary) vs. explicit topic change (a
  boundary);
- implementation -> review, test -> fix -> retest, commit -> deploy
  (normally not boundaries) vs. a genuinely new deliverable starting;
- a new tool/strategy for the *same* problem (not a boundary) vs. a move
  to a *different* problem (a boundary).

This is a semantic decision problem. M4.2a's HIGH/MEDIUM/LOW class is
supporting evidence for that decision, never the decision itself.

## 3. Semantic decision definition

M4.2b resolves each boundary candidate to exactly one of:

- **SAME_EPISODE** — same coherent professional task, problem, decision,
  or deliverable, including its normal implementation, review, testing,
  debugging, correction and immediate follow-up.
- **BOUNDARY** — a new coherent professional work unit begins, with a
  materially different goal, problem, or deliverable, even if it belongs
  to the same project.
- **UNCERTAIN** — the supplied context is insufficient, or the
  transition itself does not allow a reliable decision.

Important distinctions the resolver must respect (see `prompt.py`,
`TASK_INSTRUCTION`): substep progression, Q&A, implementation/review,
test/fix/retest, and strategy changes for the same problem are *not*
boundaries by themselves; a new deliverable or an explicit move to a
different problem *can* be. Time gap, lexical shift, and markers are
evidence, never proof.

## 4. Request contract

`tools/semantic_boundary/models.py::SemanticResolutionRequest`:

| field | type | notes |
|---|---|---|
| `candidate_id` | `str` | identity of the candidate transition |
| `conversation_id` | `str` | |
| `before_node_id` | `str` | |
| `after_node_id` | `str` | |
| `before_context` | `List[DialogueTurn]` | up to 2 turns, ends with `before_node_id` |
| `after_context` | `List[DialogueTurn]` | up to 2 turns, starts with `after_node_id` |
| `m4_2a_evidence` | `SemanticEvidence` | compact evidence subset, see §6 |
| `resolver_version` | `str` | defaults to `RESOLVER_VERSION = "m4.2b-0.1"` |

`DialogueTurn`: `node_id`, `role`, `text`, `content_type` (optional).
Never includes `thoughts`/`reasoning_recap` nodes — only visible dialogue
turns (`text`/`multimodal_text`) as already filtered by M4.2a's Dialogue
Timeline Projection.

`validate_request()` enforces: required identity strings non-empty,
non-empty before/after context, endpoint inclusion, valid evidence. It
never fails silently — every violation raises `RequestValidationError`
with a specific message.

## 5. Output contract

`tools/semantic_boundary/models.py::SemanticResolution`:

`candidate_id`, `decision` (`SAME_EPISODE`/`BOUNDARY`/`UNCERTAIN`),
`confidence` (`float` in `[0.0, 1.0]`), `reason` (short, human-readable,
auditable, semantic — never chain-of-thought), `resolver_version`,
`judge_name`, `judge_version`, `resolution_hash`.

`validate_resolution()` / `validate_decision()` / `validate_confidence()`
reject invalid decisions and out-of-range confidence explicitly.

### Confidence semantics

`confidence` is the judge's self-reported confidence / the resolver's
confidence in the decision. **It is not a globally calibrated
probability** unless a future validation pass proves otherwise against a
larger gold set. No calibration is attempted in this pass.

## 6. Context-window policy v0.1

`tools/semantic_boundary/context.py::clip_context()`:

- up to 2 visible dialogue turns before the candidate, up to 2 after;
- the endpoint turns (`before_node_id`, `after_node_id`) are always
  included;
- order and role are preserved exactly as in the supplied timeline;
- no retrieval, no other conversations, no hidden project memory — the
  judge decides only from what's in the request.

`clip_context()` raises `RequestValidationError` if either endpoint is
missing from the supplied timeline, or if `after_node_id` does not occur
strictly after `before_node_id` — it never silently returns a truncated
or empty window.

## 7. Evidence policy

`SemanticEvidence` (in `models.py`) is a **compact, decoupled** subset of
M4.2a's `BoundaryCandidate` (`tools/episodes/models.py`, on branch
`feature/m4.2a-boundary-candidates`): `candidate_class`, `candidate_score`,
`time_gap_seconds`, `time_gap_bucket`, `lexical_shift_score`,
`opening_markers`, `closure_markers`, `resume_markers`,
`transition_markers`, `intermediate_node_count`.

M4.2b deliberately does **not** import `tools.episodes` — the same
autonomy M4.2a's own `hashing.py` already applies toward M4.1. Callers
(a future Episode Builder or CLI, not built in this pass) are responsible
for mapping a real `BoundaryCandidate.to_dict()` onto this compact shape.
This evidence is supporting information only: `resolver.py` and
`evaluation.py` never derive the decision from `candidate_class` alone.

## 8. SemanticJudge abstraction

`tools/semantic_boundary/judge.py`:

```python
class SemanticJudge(ABC):
    def resolve(self, request: SemanticResolutionRequest) -> JudgeResponse: ...
```

`JudgeResponse` carries `decision`, `confidence`, `reason`, `judge_name`,
`judge_version` — not `candidate_id`/`resolver_version`/`resolution_hash`,
which are assembled by the resolver, not the judge. `JudgeError` signals
a judge failure and is never swallowed by the runner silently; batch runs
capture it as an explicit `ResolutionFailure` instead.

No real adapter exists yet. Future work (out of scope here): a cloud
judge, an Ollama/local judge — both must implement this same interface.

### Fixture judge

`FakeSemanticJudge` is deterministic infrastructure-only: a configurable
default response, optional per-`candidate_id` canned responses, and an
optional set of `candidate_id`s that trigger `JudgeError`. It performs no
semantic reasoning and must not be mistaken for a real judge.

## 9. Deterministic judge-input preparation

`tools/semantic_boundary/prompt.py` builds the structured payload
(`build_judge_input()`) and a deterministic plain-text rendering
(`render_judge_prompt()`) that future adapters will send to a real model.
`TASK_INSTRUCTION` is the static English instruction text (task
definition, SAME_EPISODE/BOUNDARY/UNCERTAIN definitions, important
distinctions, and an explicit "no chain-of-thought" output requirement).
No LLM is called in this pass — this module only prepares input.

## 10. Runner

`tools/semantic_boundary/resolver.py`:

- `build_request(candidate: dict, visible_turns, ...)` — builds and
  validates a `SemanticResolutionRequest` from a raw compact candidate
  record (see §7) and a conversation's full visible-turn timeline, using
  `clip_context()`. Raises `RequestValidationError` on any malformed
  candidate record (missing fields).
- `resolve_candidate(request, judge)` — calls the judge, validates its
  response, computes `resolution_hash`, returns a validated
  `SemanticResolution`. Propagates `JudgeError`/validation errors.
- `run_resolutions(candidates_with_turns, judge)` — batch runner; a
  single candidate's failure (malformed record or judge failure) is
  captured as a `ResolutionFailure(candidate_id, error_type,
  error_message)` and does not abort the rest of the batch. Failures are
  always explicit, never dropped.

## 11. Hashing / determinism

`tools/semantic_boundary/hashing.py` follows the same canonical-JSON +
SHA-256 convention already established by `tools/chatgpt/hashing.py` and
`tools/episodes/hashing.py` (UTF-8, sorted keys, stable separators,
non-ASCII preserved), but is implemented autonomously — no cross-import
with either. `compute_request_hash()` hashes the full canonical request;
`compute_resolution_hash()` hashes the resolution's normalized fields
(never itself). Same semantic input always produces the same request; no
random UUIDs anywhere in the package.

## 12. Gold Pilot evaluator

`tools/semantic_boundary/evaluation.py`.

### Gold label mapping

| `gold_label` | expected `decision` |
|---|---|
| `TRUE` | `BOUNDARY` |
| `FALSE` | `SAME_EPISODE` |
| `AMBIGUOUS` | `UNCERTAIN` |

### Input format (external files, never committed to this repo)

`gold-pilot-labeled.jsonl`: one JSON object per line, at minimum
`{"candidate_id": "...", "gold_label": "TRUE"|"FALSE"|"AMBIGUOUS"}`.

`resolutions.jsonl`: one JSON object per line, at minimum
`{"candidate_id": "...", "decision": "SAME_EPISODE"|"BOUNDARY"|"UNCERTAIN",
"confidence": 0.0-1.0}`.

### CLI

```
python3 -m tools.semantic_boundary.evaluation \
    /path/to/gold-pilot-labeled.jsonl \
    /path/to/resolutions.jsonl
```

Prints a JSON report to stdout; exits `1` with a message on stderr for
any malformed/duplicate/missing record — never a silent partial result.

### Metrics

`records` (gold/resolution counts and matched count), `exact_matches`,
`accuracy`, a full `SAME_EPISODE`/`BOUNDARY`/`UNCERTAIN` confusion
matrix, precision/recall/F1 for `BOUNDARY` and for `SAME_EPISODE`,
`expected_uncertain_count`/`actual_uncertain_count`, and explicit lists
of `gold_only_candidate_ids` / `resolution_only_candidate_ids` (never
silently dropped from the report). Standard library only — no ML
dependencies.

**Important evaluation principle:** the evaluator compares decisions
against manual Gold labels only. A resolver that maps
`candidate_class` directly to a decision (e.g. `HIGH -> BOUNDARY`) is
architecturally invalid even if it happened to score well on this small
sample — this is a review rule for any future judge implementation, not
something the evaluator itself can detect.

## 13. Limitations

- Gold Pilot 001 has only 5 TRUE (boundary) cases out of 60. Its metrics
  are a **pilot diagnostic**, not a statistically robust benchmark — do
  not treat precision/recall/F1 from it as production-grade numbers.
- `confidence` is not calibrated.
- Context window v0.1 is fixed at 2 turns each side; no experimentation
  with window size is in scope here.
- No real judge exists yet, so end-to-end semantic accuracy is untested
  by this pass — only the infrastructure around a judge is.

# M4.2b-B — OllamaSemanticJudge (local adapter)

Status: **PASS 2 — first real `SemanticJudge` implementation, local-only,
implementation-only pass. No real Gold Pilot run has been executed by
this pass (§16.6). M4.2a and M4.2b-A are unmodified.**

## 16.1 Purpose

Connects the M4.2b-A contract (§4–§11 above) to a local Ollama instance,
validated first against `llama3.1:8b`. This is the first *real* judge:
previously only `FakeSemanticJudge` existed. Everything in §1–§15 above
is unchanged — `OllamaSemanticJudge` implements the same
`SemanticJudge.resolve()` interface (§8) and produces the same
`JudgeResponse`/`SemanticResolution` shapes.

Module: `tools/semantic_boundary/ollama.py`. Single file, following the
existing convention of `evaluation.py` (judge/runner logic + CLI in one
module). No new dependency: `urllib.request`/`urllib.error` (standard
library) only.

## 16.2 Architecture: local-only

```
SemanticResolutionRequest
    -> render_judge_prompt() [prompt.py, UNCHANGED]
    -> + OUTPUT_FORMAT_INSTRUCTION [ollama.py, format-only, no semantic tuning]
    -> POST {OLLAMA_BASE_URL}/api/generate  (non-streaming, format=json, temperature=0)
    -> structured JSON {decision, confidence, reason}
    -> validated against models.py contract
    -> JudgeResponse
```

- **Default endpoint**: `http://127.0.0.1:11434` (`DEFAULT_OLLAMA_BASE_URL`).
  Never a hard-coded remote Atlas address. Configurable via
  `OllamaSemanticJudge(base_url=...)`, the `OLLAMA_BASE_URL` environment
  variable, or `--ollama-url` on the CLI (constructor argument takes
  precedence, then the env var, then the default).
- **Default model**: `llama3.1:8b` (`DEFAULT_MODEL`), configurable via
  `--model` / the `model=` constructor argument. The adapter never
  branches its behavior on the model name.
- **API mode**: `/api/generate`, `"stream": false` — a single
  non-streaming call per candidate. No tools, no web, no retrieval, no
  conversation memory across candidates.
- **Determinism**: `"options": {"temperature": 0.0}` always; an optional
  `seed` (constructor/`--seed`) is forwarded when set. As documented
  already in general LLM-serving practice: **even with temperature 0 and
  a fixed seed, local LLM inference may not be perfectly
  bit-for-bit deterministic** (batching, kernel non-determinism, engine
  version). This adapter does not claim otherwise.
- **Timeout**: configurable, default `120.0` seconds
  (`DEFAULT_TIMEOUT_SECONDS`) — conservative for an 8B model on a local
  NUC. A timeout always raises `OllamaTimeoutError` (a `JudgeError`
  subclass); it is never silently swallowed or retried.

## 16.3 Structured output contract

The model is asked (via `OUTPUT_FORMAT_INSTRUCTION`, appended after
M4.2b-A's `TASK_INSTRUCTION` + context + evidence — the semantic task
text itself is untouched) to return exactly:

```json
{"decision": "SAME_EPISODE | BOUNDARY | UNCERTAIN", "confidence": 0.0-1.0, "reason": "short reason"}
```

No chain-of-thought is requested or stored — only `decision`,
`confidence`, `reason`, matching M4.2b-A's `JudgeResponse` shape exactly.
The request also sets Ollama's own `"format": "json"` to bias the model
toward syntactically valid JSON, but the adapter never trusts that alone:
every response is parsed and validated against `models.py`
(`validate_decision`, `validate_confidence`) before being accepted.

The parsed JSON object's key set is checked exactly against
`{"decision", "confidence", "reason"}`: an object missing one of these
keys, or carrying any additional key (e.g. a leaked
`"chain_of_thought"`), is treated the same as unparseable JSON — it does
not reach decision/confidence/reason validation at all.

**Never accepted as valid**: free-form prose, a JSON object with
missing or additional keys, decisions outside
`{SAME_EPISODE, BOUNDARY, UNCERTAIN}`, confidence outside `[0.0, 1.0]`,
missing/empty `reason`. Any of these raise `OllamaResponseError` (a
`JudgeError` subclass) — never a silent guess or a default decision.

## 16.4 Error handling and retry policy

| Failure | Exception (all subclass `JudgeError`) | Retry |
|---|---|---|
| Connection refused / transport-level failure | `OllamaTransportError` | **one** technical retry, identical request; second failure propagates |
| Timeout | `OllamaTimeoutError` | none — surfaced immediately |
| Non-200 HTTP status | `OllamaHTTPError` | none — surfaced immediately |
| Unparseable/malformed structured JSON (incl. wrong key set) | `OllamaResponseError` | **one** repair retry with the exact same semantic input; a second malformed/unparseable response raises `OllamaResponseError` |
| Valid JSON but invalid `decision`/`confidence`/`reason` value | `OllamaResponseError` | none — this is a validation failure, not a malformed-JSON case, so it does not consume the repair retry |

If the repair-retry HTTP call itself fails at the infrastructure level
(connection refused, timeout, non-200 status), that failure is **never**
reclassified as `OllamaResponseError`: it propagates with its own
explicit type (`OllamaTransportError` / `OllamaTimeoutError` /
`OllamaHTTPError`), exactly as a first-attempt failure would. Only a
second malformed/unparseable *response body* — not a transport/HTTP/
timeout failure — produces `OllamaResponseError` from the repair path.
This keeps the error taxonomy meaningful: a caller can always tell
"the model produced garbage twice" apart from "the second attempt never
reached the model."

No self-consistency voting, no majority-of-N, no model cascade, no cloud
fallback. This validates exactly one judge, not an ensemble — per the
M4.2b-B mandate. All failure types subclass the existing `JudgeError`
(`judge.py`), so `resolver.py`'s existing `run_resolutions`/batch error
handling (§10 above) requires **no modification** to catch them.

### 16.4.1 Constructor configuration guardrails

`OllamaSemanticJudge.__init__` validates its resolved configuration
before any request is ever made, raising `ValueError` immediately for:

- `model`: must be a non-empty (non-whitespace) string;
- `base_url` (after the `base_url=` / `OLLAMA_BASE_URL` / default
  fallback chain in §16.2 above): must resolve to a non-empty
  (non-whitespace) string;
- `timeout`: must be a number `> 0`.

This is plain, explicit validation in `__init__` — no configuration
framework or new dependency.

## 16.5 Privacy and logging

- Dialogue text is sent only to the configured Ollama endpoint.
- With the default `127.0.0.1` endpoint, no conversation content leaves
  the local machine (Atlas, once transferred there).
- Diagnostic logging (`logging` module, logger
  `tools.semantic_boundary.ollama`) emits only `candidate_id`, `model`,
  `status` (`ok`/`error`), `latency_ms`, and `error_type` on failure. It
  **never** logs the prompt body or the model's response text.

## 16.6 Gold leakage protection

`build_request_from_gold_pilot_record()` reads only a fixed, explicit
list of fields (`_REQUIRED_RECORD_FIELDS`) from an external Gold Pilot
record. `gold_label` and `gold_notes` are **not** in that list: even if
present in the source file, they are never read, never placed on the
`SemanticResolutionRequest`, and therefore structurally cannot reach
`render_judge_prompt()` or the HTTP payload — this is enforced by
construction (the dataclass has no such field), not by a runtime filter
that could be bypassed. Covered by test `test_gold_label_and_notes_are_never_sent_to_the_judge`.

### External Gold Pilot record format (M4.2b-B convention, not committed to this repo)

One JSON object per line, with the same flat fields already required by
`resolver.build_request` (§7/§10 above) **plus already-clipped**
`before_context`/`after_context` (lists of `DialogueTurn`-shaped dicts:
`node_id`, `role`, `text`, optional `content_type`):

```json
{
  "candidate_id": "...", "conversation_id": "...",
  "before_node_id": "...", "after_node_id": "...",
  "candidate_class": "HIGH|MEDIUM|LOW", "candidate_score": 0.0,
  "time_gap_seconds": 120.0, "time_gap_bucket": "short",
  "lexical_shift_score": 0.3,
  "opening_markers": [], "closure_markers": [], "resume_markers": [], "transition_markers": [],
  "intermediate_node_count": 0,
  "before_context": [{"node_id": "...", "role": "...", "text": "...", "content_type": "text"}],
  "after_context": [{"node_id": "...", "role": "...", "text": "...", "content_type": "text"}],
  "gold_label": "TRUE|FALSE|AMBIGUOUS",
  "gold_notes": "optional annotator note"
}
```

`gold_label`/`gold_notes` are only ever used later, offline, by
`evaluation.py` against the *output* `resolutions.jsonl` — never as
judge input. The **2-before/2-after context-window policy itself is
unchanged** (§6 above, `context.py`); this format simply expects the
window to already have been clipped by whoever produced the Gold Pilot
file, since a human annotator needs to see that same context to assign
`gold_label` in the first place.

## 16.7 Model metadata

`SemanticResolution`/`JudgeResponse` (`models.py`, `judge.py`) have no
dedicated `model` field, and this pass does **not** alter that schema
(per the M4.2b-B mandate: a schema change requires stopping and
reporting first — no incompatibility was found that would require one).
Model identity is instead carried in the existing `judge_version` field:
`judge_name = "ollama"`, `judge_version = "0.1+<model>"` (e.g.
`"0.1+llama3.1:8b"`). This is fully sufficient to distinguish runs across
models without a serialized-schema change.

## 16.8 CLI / batch runner

```
python3 -m tools.semantic_boundary.ollama \
    /path/to/gold-pilot-labeled.jsonl \
    /path/to/resolutions.jsonl \
    --model llama3.1:8b \
    --ollama-url http://127.0.0.1:11434 \
    [--timeout 120] [--seed N] [--failures-path /path/to/failures.jsonl]
```

Writes successful `SemanticResolution` records (§5 above) as JSONL to
`resolutions.jsonl`, directly consumable by `evaluation.py` unchanged.
Failures (malformed records or any `JudgeError`, including all
`OllamaError` subtypes) are **never dropped**: they are written
explicitly, one JSON object per line
(`candidate_id`/`error_type`/`error_message`), to a companion file
(default `<output_path>.failures.jsonl`, overridable with
`--failures-path`).

# M4.2b-C — Semantic Judge Instruction v0.2 (prompt-only experiment)

Status: **PASS 3 — prompt-only change. No real Ollama run performed by
this pass. RESULT is pending the real Gold Pilot run on Atlas (§17.8).**

## 17.1 OBSERVATION

The real `llama3.1:8b` run on Gold Pilot 001 (§16.9 procedure, executed
separately on Atlas) produced, with `TASK_INSTRUCTION` v0.1:

- `accuracy = 0.7666666666666667`
- BOUNDARY: TP=1, FP=9, FN=4, precision=0.10, recall=0.20, F1=0.1333...
- SAME_EPISODE: TP=45, precision=0.90, recall=0.8333..., F1=0.8654...
- `UNCERTAIN` produced by the model: 0 times.
- Of the 5 Gold TRUE (boundary) transitions, only one was classified
  `BOUNDARY`.

Inspection of the model's `reason` fields showed a recurring pattern: the
model often correctly describes an operational change (e.g. a new
concrete task starting) but still returns `SAME_EPISODE`, apparently
because it overweights continuity of project, customer, system, or
general topic rather than continuity of the concrete work unit itself.

A second, independent observation: in some resolutions the returned
`confidence` was numerically close to M4.2a's `candidate_score`.
`candidate_score` is a Boundary Evidence Score produced by the
deterministic upstream detector (§2, §7 above) — it is not a probability
of boundary and not a semantic confidence value, so a judge confidence
that tracks it is evidence of anchoring rather than of independent
semantic reasoning.

## 17.2 HYPOTHESIS

`TASK_INSTRUCTION` v0.1 defines `SAME_EPISODE`/`BOUNDARY` in terms of
"coherent professional task, problem, decision, or deliverable" but does
not explicitly rule out project/customer/system/topic/time-proximity as
sufficient conditions for `SAME_EPISODE`, and does not warn the judge
against anchoring its `confidence` on `candidate_score`. A more explicit,
purely operational definition of `EPISODE` — one that separates "same
project" from "same concrete work unit" and explicitly forbids deriving
confidence from `candidate_score` — may reduce the false-negative rate on
`BOUNDARY` without materially degrading `SAME_EPISODE` precision/recall,
**without** changing the model, resolver, evidence engine, adapter, or
architecture.

This hypothesis is untested until the real run in §17.8 below.

## 17.3 EXPERIMENT: prompt-only change

## 17.5 Confidence-anchoring protections (§4 of the mandate)

v0.2 adds an explicit paragraph ("CANDIDATE_SCORE AND OTHER M4.2A
SIGNALS") instructing the judge:

- `candidate_score` is a Boundary Evidence Score, not a probability, not
  a semantic confidence, not a target confidence value;
- the judge must not copy it into `confidence`, must not derive
  `confidence` from it mathematically, must not treat `candidate_class`
  as a pre-made decision;
- `confidence` must reflect only the judge's own assessment of the
  reliability of its semantic classification, given the available
  context.

This is instruction-only: it cannot structurally prevent an LLM from
anchoring, but it makes the distinction explicit where v0.1 only implied
it ("supporting, not decisive").
