# M4.2b-A — Semantic Boundary Resolver: Contract + Evaluator

Status: **PASS 1 (M4.2b-A) — infrastructure only, no real LLM provider.**

## 1. Why M4.2b exists

M4.1 (Lossless Normalizer) and M4.2a (Deterministic Boundary Evidence
Engine) are CLOSED. The verified pipeline is:

```
RAW CHATGPT EXPORT
    -> M4.1 LOSSLESS NORMALIZER
    -> ACNF / SOURCE GRAPH
    -> CURRENT PATH
    -> DIALOGUE TIMELINE PROJECTION
    -> VISIBLE DIALOGUE TRANSITIONS
    -> M4.2A DETERMINISTIC BOUNDARY EVIDENCE
    -> BOUNDARY CANDIDATES
```

Gold Pilot 001 (60 hand-labeled real candidates: 20 HIGH / 20 MEDIUM / 20
LOW by `candidate_class`; manual labels 5 TRUE / 54 FALSE / 1 AMBIGUOUS)
established that `candidate_score`/`candidate_class` are a **Boundary
Evidence Score**, not a probability of a semantic boundary. M4.2a
generates evidence; it does not decide.

## 2. Verified limitation of M4.2a

M4.2a cannot and does not distinguish, purely from deterministic
features, cases such as:

- question -> answer (not a boundary) vs. explicit topic change (a
  boundary);
- implementation -> review, test -> fix -> retest, commit -> deploy
  (normally not boundaries) vs. a genuinely new deliverable starting;
- a new tool/strategy for the *same* problem (not a boundary) vs. a move
  to a *different* problem (a boundary).

This is a semantic decision problem. M4.2a's HIGH/MEDIUM/LOW class is
supporting evidence for that decision, never the decision itself.

## 3. Semantic decision definition

M4.2b resolves each boundary candidate to exactly one of:

- **SAME_EPISODE** — same coherent professional task, problem, decision,
  or deliverable, including its normal implementation, review, testing,
  debugging, correction and immediate follow-up.
- **BOUNDARY** — a new coherent professional work unit begins, with a
  materially different goal, problem, or deliverable, even if it belongs
  to the same project.
- **UNCERTAIN** — the supplied context is insufficient, or the
  transition itself does not allow a reliable decision.

Important distinctions the resolver must respect (see `prompt.py`,
`TASK_INSTRUCTION`): substep progression, Q&A, implementation/review,
test/fix/retest, and strategy changes for the same problem are *not*
boundaries by themselves; a new deliverable or an explicit move to a
different problem *can* be. Time gap, lexical shift, and markers are
evidence, never proof.

## 4. Request contract

`tools/semantic_boundary/models.py::SemanticResolutionRequest`:

| field | type | notes |
|---|---|---|
| `candidate_id` | `str` | identity of the candidate transition |
| `conversation_id` | `str` | |
| `before_node_id` | `str` | |
| `after_node_id` | `str` | |
| `before_context` | `List[DialogueTurn]` | up to 2 turns, ends with `before_node_id` |
| `after_context` | `List[DialogueTurn]` | up to 2 turns, starts with `after_node_id` |
| `m4_2a_evidence` | `SemanticEvidence` | compact evidence subset, see §6 |
| `resolver_version` | `str` | defaults to `RESOLVER_VERSION = "m4.2b-0.1"` |

`DialogueTurn`: `node_id`, `role`, `text`, `content_type` (optional).
Never includes `thoughts`/`reasoning_recap` nodes — only visible dialogue
turns (`text`/`multimodal_text`) as already filtered by M4.2a's Dialogue
Timeline Projection.

`validate_request()` enforces: required identity strings non-empty,
non-empty before/after context, endpoint inclusion, valid evidence. It
never fails silently — every violation raises `RequestValidationError`
with a specific message.

## 5. Output contract

`tools/semantic_boundary/models.py::SemanticResolution`:

`candidate_id`, `decision` (`SAME_EPISODE`/`BOUNDARY`/`UNCERTAIN`),
`confidence` (`float` in `[0.0, 1.0]`), `reason` (short, human-readable,
auditable, semantic — never chain-of-thought), `resolver_version`,
`judge_name`, `judge_version`, `resolution_hash`.

`validate_resolution()` / `validate_decision()` / `validate_confidence()`
reject invalid decisions and out-of-range confidence explicitly.

### Confidence semantics

`confidence` is the judge's self-reported confidence / the resolver's
confidence in the decision. **It is not a globally calibrated
probability** unless a future validation pass proves otherwise against a
larger gold set. No calibration is attempted in this pass.

## 6. Context-window policy v0.1

`tools/semantic_boundary/context.py::clip_context()`:

- up to 2 visible dialogue turns before the candidate, up to 2 after;
- the endpoint turns (`before_node_id`, `after_node_id`) are always
  included;
- order and role are preserved exactly as in the supplied timeline;
- no retrieval, no other conversations, no hidden project memory — the
  judge decides only from what's in the request.

`clip_context()` raises `RequestValidationError` if either endpoint is
missing from the supplied timeline, or if `after_node_id` does not occur
strictly after `before_node_id` — it never silently returns a truncated
or empty window.

## 7. Evidence policy

`SemanticEvidence` (in `models.py`) is a **compact, decoupled** subset of
M4.2a's `BoundaryCandidate` (`tools/episodes/models.py`, on branch
`feature/m4.2a-boundary-candidates`): `candidate_class`, `candidate_score`,
`time_gap_seconds`, `time_gap_bucket`, `lexical_shift_score`,
`opening_markers`, `closure_markers`, `resume_markers`,
`transition_markers`, `intermediate_node_count`.

M4.2b deliberately does **not** import `tools.episodes` — the same
autonomy M4.2a's own `hashing.py` already applies toward M4.1. Callers
(a future Episode Builder or CLI, not built in this pass) are responsible
for mapping a real `BoundaryCandidate.to_dict()` onto this compact shape.
This evidence is supporting information only: `resolver.py` and
`evaluation.py` never derive the decision from `candidate_class` alone.

## 8. SemanticJudge abstraction

`tools/semantic_boundary/judge.py`:

```python
class SemanticJudge(ABC):
    def resolve(self, request: SemanticResolutionRequest) -> JudgeResponse: ...
```

`JudgeResponse` carries `decision`, `confidence`, `reason`, `judge_name`,
`judge_version` — not `candidate_id`/`resolver_version`/`resolution_hash`,
which are assembled by the resolver, not the judge. `JudgeError` signals
a judge failure and is never swallowed by the runner silently; batch runs
capture it as an explicit `ResolutionFailure` instead.

No real adapter exists yet. Future work (out of scope here): a cloud
judge, an Ollama/local judge — both must implement this same interface.

### Fixture judge

`FakeSemanticJudge` is deterministic infrastructure-only: a configurable
default response, optional per-`candidate_id` canned responses, and an
optional set of `candidate_id`s that trigger `JudgeError`. It performs no
semantic reasoning and must not be mistaken for a real judge.

## 9. Deterministic judge-input preparation

`tools/semantic_boundary/prompt.py` builds the structured payload
(`build_judge_input()`) and a deterministic plain-text rendering
(`render_judge_prompt()`) that future adapters will send to a real model.
`TASK_INSTRUCTION` is the static English instruction text (task
definition, SAME_EPISODE/BOUNDARY/UNCERTAIN definitions, important
distinctions, and an explicit "no chain-of-thought" output requirement).
No LLM is called in this pass — this module only prepares input.

## 10. Runner

`tools/semantic_boundary/resolver.py`:

- `build_request(candidate: dict, visible_turns, ...)` — builds and
  validates a `SemanticResolutionRequest` from a raw compact candidate
  record (see §7) and a conversation's full visible-turn timeline, using
  `clip_context()`. Raises `RequestValidationError` on any malformed
  candidate record (missing fields).
- `resolve_candidate(request, judge)` — calls the judge, validates its
  response, computes `resolution_hash`, returns a validated
  `SemanticResolution`. Propagates `JudgeError`/validation errors.
- `run_resolutions(candidates_with_turns, judge)` — batch runner; a
  single candidate's failure (malformed record or judge failure) is
  captured as a `ResolutionFailure(candidate_id, error_type,
  error_message)` and does not abort the rest of the batch. Failures are
  always explicit, never dropped.

## 11. Hashing / determinism

`tools/semantic_boundary/hashing.py` follows the same canonical-JSON +
SHA-256 convention already established by `tools/chatgpt/hashing.py` and
`tools/episodes/hashing.py` (UTF-8, sorted keys, stable separators,
non-ASCII preserved), but is implemented autonomously — no cross-import
with either. `compute_request_hash()` hashes the full canonical request;
`compute_resolution_hash()` hashes the resolution's normalized fields
(never itself). Same semantic input always produces the same request; no
random UUIDs anywhere in the package.

## 12. Gold Pilot evaluator

`tools/semantic_boundary/evaluation.py`.

### Gold label mapping

| `gold_label` | expected `decision` |
|---|---|
| `TRUE` | `BOUNDARY` |
| `FALSE` | `SAME_EPISODE` |
| `AMBIGUOUS` | `UNCERTAIN` |

### Input format (external files, never committed to this repo)

`gold-pilot-labeled.jsonl`: one JSON object per line, at minimum
`{"candidate_id": "...", "gold_label": "TRUE"|"FALSE"|"AMBIGUOUS"}`.

`resolutions.jsonl`: one JSON object per line, at minimum
`{"candidate_id": "...", "decision": "SAME_EPISODE"|"BOUNDARY"|"UNCERTAIN",
"confidence": 0.0-1.0}`.

### CLI

```
python3 -m tools.semantic_boundary.evaluation \
    /path/to/gold-pilot-labeled.jsonl \
    /path/to/resolutions.jsonl
```

Prints a JSON report to stdout; exits `1` with a message on stderr for
any malformed/duplicate/missing record — never a silent partial result.

### Metrics

`records` (gold/resolution counts and matched count), `exact_matches`,
`accuracy`, a full `SAME_EPISODE`/`BOUNDARY`/`UNCERTAIN` confusion
matrix, precision/recall/F1 for `BOUNDARY` and for `SAME_EPISODE`,
`expected_uncertain_count`/`actual_uncertain_count`, and explicit lists
of `gold_only_candidate_ids` / `resolution_only_candidate_ids` (never
silently dropped from the report). Standard library only — no ML
dependencies.

**Important evaluation principle:** the evaluator compares decisions
against manual Gold labels only. A resolver that maps
`candidate_class` directly to a decision (e.g. `HIGH -> BOUNDARY`) is
architecturally invalid even if it happened to score well on this small
sample — this is a review rule for any future judge implementation, not
something the evaluator itself can detect.

## 13. Limitations

- Gold Pilot 001 has only 5 TRUE (boundary) cases out of 60. Its metrics
  are a **pilot diagnostic**, not a statistically robust benchmark — do
  not treat precision/recall/F1 from it as production-grade numbers.
- `confidence` is not calibrated.
- Context window v0.1 is fixed at 2 turns each side; no experimentation
  with window size is in scope here.
- No real judge exists yet, so end-to-end semantic accuracy is untested
  by this pass — only the infrastructure around a judge is.
