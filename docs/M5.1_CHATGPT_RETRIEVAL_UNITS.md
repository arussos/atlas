# M5.1 — ChatGPT Retrieval Unit Projection

## Stato

Milestone: M5.1
Componente: Atlas V2 Professional Memory Layer
Tipo: deterministic projection (no LLM, no embedding, no indexing)
Input: ACNF v0.1 (acquisition.json, conversations.jsonl, nodes.jsonl)
Output: retrieval_units.jsonl
LLM usage: NONE
Projection version: 0.1

---

## 1. Scopo

M5.1 deriva unità di retrieval deterministiche e model-independent dalla
memoria ChatGPT già normalizzata (M4.1 ACNF), preservando piena
provenance verso i nodi ACNF:

    ACNF normalized conversation
        -> authoritative current-path ordering
        -> visible dialogue projection
        -> deterministic overlapping RetrievalUnit records
        -> JSONL

Un RetrievalUnit è la forma con cui un futuro layer di indicizzazione
(M5.2) vedrà la memoria conversazionale: finestre overlapping di turni
di dialogo visibili, con identità stabile, hash di contenuto e
provenance completa.

**Un RetrievalUnit NON è un episodio.** Non ha confini semantici, non
rappresenta un'unità di senso, non è il prodotto di una decisione di
boundary. È una finestra meccanica e riproducibile sulla timeline di
dialogo visibile.

## 2. Non-goals espliciti

M5.1 NON è:

- un Episode Builder;
- segmentazione semantica;
- generazione di embedding;
- vector indexing / Qdrant;
- integrazione Open WebUI;
- un retriever o reranker;
- una pipeline LLM.

Nessun modello viene invocato in nessun punto. Nessuna dipendenza da
`tools/semantic_boundary/*`, M4.2b, SemanticJudge, Ollama o boundary
confidence: M4.2b è sperimentalmente congelato e fuori dal critical
path MVP (test `tests/retrieval_units/test_isolation.py`).

## 3. Posizione architetturale e fonte di verità

ACNF (M4.1) resta l'unica fonte di verità. M5.1 consuma esclusivamente
la forma JSONL di ACNF e non la modifica mai. `RetrievalUnit.text` è
**dato derivato**, ricostruibile deterministicamente dai `node_ids`
contro ACNF.

API M4.1/M4.2a riusate (mai duplicate):

| API | Ruolo |
|---|---|
| `tools.episodes.graph.reconstruct_current_path` | ordine autorevole del current path (walk su `parent_id` da `current_node_id`; i timestamp non sono mai una fonte d'ordine) |
| `tools.episodes.projection.project_dialogue_timeline` | proiezione dialogue visibile + provenance `intermediates_before` |
| `tools.episodes.projection.VISIBLE_DIALOGUE_CONTENT_TYPES` | unica policy di visibilità (`text`, `multimodal_text`); M5.1 non ne implementa una seconda |
| `tools.episodes.text.extract_visible_text` | estrazione deterministica del testo visibile |
| `tools.episodes.boundary_candidates.select_current_path_message_nodes` | input selection autorevole dei nodi-messaggio del current path — il predicato vive solo in M4.2a, mai duplicato in M5.1 |
| `tools.episodes.boundary_candidates._index_nodes_by_conversation` | raggruppamento nodi per conversazione con semantica `duplicate_node_id` identica a M4.2a |
| `tools.episodes.models.Anomaly` | registrazione anomalie strutturali, mai eccezioni |

## 4. Policy di windowing v0.1

Deliberatamente semplice e non semantica:

- WINDOW SIZE: 6 nodi dialogue visibili;
- STRIDE: 3 nodi visibili (overlap 3 nodi / 50%);
- l'ultima finestra può contenere meno di 6 nodi e **non viene mai
  scartata**;
- ogni nodo visibile appartiene ad almeno una finestra;
- < 6 nodi visibili -> una sola unit con tutti i nodi;
- 0 nodi visibili -> zero unit.

Esempi (ordinali 1-based dei nodi visibili): 6 nodi -> 1-6; 9 nodi ->
1-6, 4-9; 14 nodi -> 1-6, 4-9, 7-12, 10-14.

Nessun token count, nessuna soglia di caratteri o di tempo, nessun
boundary semantico, nessun `candidate_score`, nessuna finestra
adattiva, nessuna invocazione di M4.2b.

Convenzione ordinali nel record: `ordinal_start` / `ordinal_end` sono
**0-based, entrambi inclusivi**, riferiti alla sola sequenza dei nodi
dialogue visibili della conversazione (coerente con `sequence_index`
0-based di M4.2a). `message_count == ordinal_end - ordinal_start + 1`.

## 5. Contratto RetrievalUnit

Campi serializzati in `retrieval_units.jsonl` (una riga per unit):

| Campo | Semantica |
|---|---|
| `retrieval_unit_id` | identità logica stabile (SHA-256 canonico, vedi §6) |
| `projection_version` | versione della policy M5.1, `"0.1"` |
| `source_type` | literal esatto `"chatgpt"` |
| `acquisition_id` | snapshot di normalizzazione da cui il record è stato prodotto |
| `acnf_schema_version` | versione schema ACNF dello snapshot |
| `conversation_id` | conversazione ACNF di appartenenza |
| `source_id` | id sorgente OpenAI della conversazione |
| `conversation_title` | titolo (solo metadata — mai iniettato nel testo) |
| `source_conversation_hash` | `conversation_hash` ACNF |
| `node_ids` | lista ordinata dei node id visibili inclusi |
| `first_node_id` / `last_node_id` | `node_ids[0]` / `node_ids[-1]` |
| `ordinal_start` / `ordinal_end` | ordinali visibili 0-based inclusivi |
| `message_count` | `len(node_ids)` |
| `start_timestamp` / `end_timestamp` | `created_at` del primo/ultimo nodo incluso; `None` se assente alla fonte — mai sintetizzato |
| `intermediate_node_ids` | provenance ordinata dei nodi tecnici saltati (vedi §8) |
| `text` | rendering derivato (vedi §7) |
| `content_hash` | rilevamento cambi materiali (vedi §6) |

## 6. Identità vs content versioning

Identità stabile e rilevamento contenuto sono deliberatamente separati
(`tools/retrieval_units/hashing.py`, autonomo come
`tools/episodes/hashing.py` — stessa convenzione canonica: JSON UTF-8,
chiavi ordinate, separatori stabili, SHA-256; mai UUID/random).

`retrieval_unit_id` = SHA-256 canonico di:

    {projection_version, conversation_id, node_ids (ordinati)}

**Non include `acquisition_id`**: la stessa unit logica che riappare in
un export ChatGPT successivo con identica identità conversation/node
resta riconoscibilmente la stessa unit.

`content_hash` = SHA-256 canonico di:

    {retrieval_unit_id, text, node_hashes (ACNF, ordinati),
     intermediate_node_ids}

Se la stessa identità logica cambia contenuto tra acquisizioni:
`retrieval_unit_id` resta stabile, `content_hash` cambia. I `node_hash`
ACNF coprono anche cambi sorgente che non alterano il testo estratto
(es. `asset_refs`); la provenance intermedia partecipa perché saltare
un insieme diverso di nodi tecnici è una unit materialmente diversa
(stessa scelta di M4.2a per `candidate_hash`).

`projection_version` partecipa all'identità: un cambio di policy
(window/stride/rendering) incrementa la versione e non colliderà mai
con le identità v0.1.

## 7. Rendering del testo

Deterministico, ricostruibile dai `node_ids`, per ogni nodo visibile in
ordine di grafo:

    [<role>]
    <testo da extract_visible_text>

blocchi uniti da una riga vuota (`\n\n`). Role mancante (mai osservato
per nodi visibili) renderizza come `[unknown]` — mai un crash.

Il testo non contiene: riassunti semantici, testo generato da LLM,
contenuto di nodi tecnici nascosti, titolo della conversazione (il
titolo resta metadata — nessuna ragione documentata per iniettarlo).

## 8. Nodi tecnici intermedi

Design scelto: **A** — provenance id-only. `project_dialogue_timeline`
restituisce `intermediates_before`; ogni unit espone
`intermediate_node_ids`, la lista ordinata dei nodi non visibili
saltati **strettamente tra** i nodi visibili inclusi nella finestra. I
nodi tecnici prima del primo nodo della finestra appartengono alla
provenance della coppia precedente (stessa attribuzione di M4.2a). Il
loro contenuto non entra mai in `text`; resta interamente recuperabile
in ACNF via node id.

## 9. Asset

M5.1 non ingerisce né renderizza contenuti di asset: nessuna estrazione
PDF, nessuna analisi immagini/audio, nessun retrieval multimodale. Gli
`asset_refs` a livello di nodo restano recuperabili attraverso la
provenance ACNF dei `node_ids`; nessun campo asset è esposto sul
RetrievalUnit v0.1 (rimandato a milestone future).

## 10. Provenance di acquisizione

Ogni record riporta `acquisition_id` e `acnf_schema_version` dello
snapshot da cui è stato materialmente prodotto. Un layer futuro può
quindi distinguere: identità logica stabile (`retrieval_unit_id`) vs
provenance di acquisizione (`acquisition_id`) vs versione di contenuto
(`content_hash`). La deduplicazione cross-acquisition NON è implementata
in M5.1 — M5.1 espone solo i metadata perché M5.2 possa farla
correttamente.

## 11. Output JSONL e determinismo

Unico formato di output: `retrieval_units.jsonl`, una riga per record,
`json.dumps(sort_keys=True, ensure_ascii=False)` — stessa convenzione
di M4.1/M4.2a.

Garanzie:

- stesso input normalizzato + stessa projection version -> byte
  identici (testato);
- ordine conversazioni: l'ordine deterministico di
  `conversations.jsonl` ereditato dalla pipeline M4.1;
- dentro ogni conversazione: unit ordinate per `ordinal_start`
  crescente;
- nessuna unit attraversa un confine tra conversazioni.

CLI (stessa forma di M4.1/M4.2a):

    python3 -m tools.retrieval_units.projection <acnf_dir> <output_dir>

`<acnf_dir>` deve contenere `acquisition.json`, `conversations.jsonl`,
`nodes.jsonl`. Le anomalie strutturali (current node mancante, parent
dangling, ciclo, node_id duplicato) sono registrate e contate, mai
sollevate come eccezioni.

## 12. Relazioni future

- **M5.2 Atlas Retriever**: consumerà `retrieval_units.jsonl` per
  embedding/indicizzazione/dedup cross-acquisition. M5.1 non sa nulla
  di vettori: espone solo identità, contenuto e provenance sufficienti.
- **Episodes / M4.2b (opzionale, futuro)**: se un giorno esisterà una
  segmentazione in episodi validata, potrà diventare una projection
  *alternativa* con una propria `projection_version` — non un
  rimpiazzo del contratto RetrievalUnit. Le identità non collideranno
  per costruzione (§6).
